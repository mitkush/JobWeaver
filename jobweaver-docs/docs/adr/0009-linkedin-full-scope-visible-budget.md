# LinkedIn via Bright Data: full scope, daily 24-hour windows, visible budget

Bright Data's free tier gives 5,000 credits a month at 1 credit per scraped record, so the budget is a number of records, whatever the fetch frequency. LinkedIn runs daily with the "past 24 hours" filter: the same cost as fetching every 3 days, no records paid twice through a coarser "past week" filter, and fresher Jobs. A missed day is caught up with the smallest filter that reaches back to the last successful run (e.g. "past week" for that one run), accepting that already-stored records are paid for again. **Every result of every query is fetched**: the founder chose not to shorten LinkedIn's scope, because its Postings are the most genuine, so JobWeaver never truncates results or caps the Backfill to fit the budget. Instead the budget is made visible: spend per query and a month-end projection, with a warning naming the date it will run out and the most expensive queries, so the Admin can narrow Preferences deliberately. If the budget runs out, LinkedIn is Degraded until renewal and the other Sources keep the Feed alive (ADR-0003). In the first month only the founder uses LinkedIn; friends are added once the real monthly spend is known. There is no per-user quota.

**Considered and rejected:** daily pacing and a Backfill cap (silently drops jobs when a search returns more than its share, the opposite of the founder's goal), fetching every 3 days (same cost, staler jobs, possible double payment), per-user quotas (the founder chose a shared pool for a small trusted group).

**Consequences:** with many title and location combinations the budget can run out before renewal, leaving LinkedIn dark until it renews; this is accepted and always visible on Source Status and in the Feed. Checked 5 Oct 2026: the Bright Data "Discover jobs by keyword" scraper is used with time ranges "Past 24 hours", "Past week" and "Past month", and returns up to 1,000 Postings per keyword call; the complete option list is confirmed in the Bright Data dashboard when building the adapter.


## Amendment: error-driven credential fallback (15 Oct 2026)

The founder chose ordered Bright Data credentials for keyword discovery, selected from provider responses rather than local quota estimates. The trigger tries the next configured key only on explicit credit/quota exhaustion or HTTP 429 before a snapshot starts. Bright Data also switches on the exact case-insensitive `Customer is not active` message on HTTP 400 or 403 from the trigger request. This is an inactive account, not a quota diagnosis; other HTTP 400 responses keep the normal failure path. A temporary HTTP 429 is retried once on the same key after three seconds before switching. Exhausting all configured keys marks the Source Degraded so its Standby can run (ADR-0016). Credentials rejected during one Source run are retried on the next; no balance endpoint, quota counters or renewal schedule is added for credential selection. Existing Fetch Run spend remains diagnostic and does not gate Bright Data searches. General errors and errors after a snapshot starts retain the normal failure path to avoid starting duplicate searches.

## Amendment: discovery keywords (15 Oct 2026)

Searching one exact title per city missed Jobs whose title differs but which match a User's Preferences. The founder chose broad role keywords instead: with `BRIGHTDATA_DISCOVERY_KEYWORDS` set, Bright Data runs one search per Preference country with the keywords joined by OR, and the Feed applies titles, places and Core keywords. A live search on 15 Oct 2026 confirmed that LinkedIn honours OR: `Zqxwvt OR Developer` returned developer jobs. Each search sends `limit_per_input` (default 1,000, Bright Data's per-call maximum, so in practice no lower than the provider's own limit). This is a per-search ceiling on cost, not budget pacing: a search that reaches it shows as "incomplete" in Recent runs so the founder can split it, and no result is silently dropped below the provider's own maximum. Empty keywords keep the per-title searches. A new discovery search continues from the oldest watermark of the per-title searches it replaces, so switching never leaves a gap; with no such history it uses the normal Backfill, visibly marked if capped. A Preference with no place searches remote work only (founder decision, 15 Oct 2026): a worldwide search of on-site and hybrid jobs returns jobs an Indian User cannot attend and fills the cap with them.
